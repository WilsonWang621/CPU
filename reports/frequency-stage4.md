# 默认综合优化，阶段 4

目标仍是原样 `make synth` 超过 300 MHz、面积不超过 36,000 μm²、六项性能测试 IPC 几何平均不低于 1.0985。阶段 3 基点为 94.17824 MHz、29,059.66 μm²、IPC 1.17233064。当前已验证版本 v24 实测为 **153.78 MHz、34,321.77 μm²、IPC 1.12820826**，19 项正确性全部通过。相对阶段 3 频率提高约 63.3%；300 MHz 目标尚未达到。

## 参考仓库复测

参考 [RISC-V-CPU-2026](https://github.com/tianhangj/RISC-V-CPU-2026) 的提交 [f3ed8dd3](https://github.com/tianhangj/RISC-V-CPU-2026/commit/f3ed8dd3bbaf0caae0b245e20bdd0f5ef95477c4)。两个仓库的 `scripts/synth.py` 逐字节相同。本地通过本仓库默认综合脚本、相同 AppImage 和时序约束复测，得到 **331.39159 MHz、3.017578125 ns、6,569.85 μm²**。其提交说明中的 331.42 MHz 与复测基本一致。

```sh
make synth FILELIST=build/frequency-stage4/reference-tianhangj/verilog/filelist.f \
  SYNTH_OUT=build/frequency-stage4/reference-standard
make build FILELIST=build/frequency-stage4/reference-tianhangj/verilog/filelist.f \
  BUILD=build/frequency-stage4/reference-sim JOBS=4
make perf SIM=build/frequency-stage4/reference-sim/sim LATENCY=20 MAX_CYCLES=30000000
```

但这个频率不能直接作为满足当前限制的架构示例：

| 项目 | 本仓库基点 | 参考仓库默认配置 |
| --- | --- | --- |
| 发射 / 派发 / 提交宽度 | 2 / 2 / 2 | 1 / 1 / 1 |
| ROB | 32 | 16 |
| 检查点 | 4 | 1 |
| 数据缓存 | 2 KiB | 无数据缓存 |
| 指令缓存存储 | 寄存器阵列，组合读 | FakeRAM，同步读 |
| 六项 IPC 几何平均，内存延迟 20 | 1.17233064 | **0.16815439** |

参考仓库的六项输出均通过性能测试的答案校验，但 IPC 不满足我们的下限。单提交宽度本身也不能支持大于 1 的长期提交 IPC。参考仓库没有在这里做完整正确性认证。

值得借鉴的是具体的时序结构：

- [issue_sched.sv](https://github.com/tianhangj/RISC-V-CPU-2026/blob/f3ed8dd3bbaf0caae0b245e20bdd0f5ef95477c4/verilog/issue_sched.sv) 在 IQ 选择、PRF 读取和执行之间保存执行包；IQ 关闭同拍唤醒后立即选择的旁路。
- [wb_arb.sv](https://github.com/tianhangj/RISC-V-CPU-2026/blob/f3ed8dd3bbaf0caae0b245e20bdd0f5ef95477c4/verilog/wb_arb.sv) 的 `PIPELINED=1` 保存结果，发布前再次检查恢复年龄边界。
- [prf.sv](https://github.com/tianhangj/RISC-V-CPU-2026/blob/f3ed8dd3bbaf0caae0b245e20bdd0f5ef95477c4/verilog/prf.sv) 用每组 8 项的两级读取，控制译码和数据扇出。
- [icache.sv](https://github.com/tianhangj/RISC-V-CPU-2026/blob/f3ed8dd3bbaf0caae0b245e20bdd0f5ef95477c4/verilog/icache.sv) 使用课程支持的同步 SRAM；标签逐项比较，数据、标签和替换信息逐项写入。

本仓库的 IPC 余量仅允许基点下降约 6.3%，因此不能直接叠加多个流水级，也不能照搬单发射和移除数据缓存的配置。

## 瓶颈与下一步方案

基点的最差路径从 ROB head 到数据缓存 pending address，head 及随后控制节点扇出达到数百。v7 表明仅插入逻辑恒等的分发树不能解决选择、分支运算和恢复控制在同周期串联的问题。

v9 把分支执行后的恢复和训练元数据寄存一拍，保留原来的结果写回周期。晚到的恢复在当拍阻止年轻指令提交，并取消年轻分支、乘除法和 load/store；检查点保留到恢复周期。必须保存训练历史，不能继续读取下一条被选中指令的 history。定向测试覆盖恢复时提交、ROB 回绕、年轻 store/branch 取消和预测历史。

后续按实际最差路径推进：

1. **IQ 年龄比较去掉 head 输入。** 给槽号增加一位分配回绕信息；所有活跃标签的跨度小于标签空间的一半，用标签差的符号比较年龄。重定向时恢复分配回绕位。此方案不增加周期，先检查六项性能周期是否逐项相同，再看默认综合收益。
2. **只拆分 IQ 宽读的控制边界。** 每个局部读取控制最多 32 位，避免一个晚到选择信号驱动整个约 188 位执行包。此前对所有读端同时拆分失败，不能直接假设这个局部版本会提高频率。
3. **局部化操作数唤醒和写回译码。** 最差路径尾部到内存 IQ 操作数寄存器；先控制该路径的写入扇出。若仍需写回流水级，先测 IPC，低于 1.0985 就回退。
4. **最后评估同步缓存 / 执行分级。** 这更接近参考仓库的时序划分，也会改变命中或依赖延迟。必须配合预测或调度改进补回 IPC，并使用课程计面积、计时序的 SRAM 模型。当前没有证据保证这些改动能达到 300 MHz。

v10 的最差路径转到前端 PC、指令读取、分支立即数加法和取指队列。v12 把 JAL / 条件分支的完整目标地址在缓存填充时算好，与原指令一起保存；缓存有效性和完整地址标签共同保证读取到的目标属于这条指令。新测试在缓存索引别名、重定向、存储响应停顿和错误下检查正/负偏移及目标为 PC+4 的情况。六项性能周期与 v9 逐项一致。

v12 的关键路径已经精确追到 `core.head[1] → core.architectural[14][0]`。通过相同综合前端导出的中间网表核对原始寄存器，记录在 [critical-path-origin.json](data/2026-10-02/timing-stage4/v12/critical-path-origin.json)。该路径前三个节点扇出 258、137、113，累计延迟 4.5941 ns，已超过整个 300 MHz 周期。v17 把退休所需的元数据和值改为旋转单热读取，并把双提交写入译码放到每个架构寄存器内，但频率只有 124.91 MHz。继续追踪发现退休许可仍调用通用圆环年龄比较；v19 将双提交的判断化简：第 0 条始终位于恢复边界内，第 1 条只有在恢复分支等于 head 时位于边界外。因此只需判断 `lane==0 || !redirect || redirect_rid!=head`。这是双退休结构的等价变换，不增加周期；组合单元测试穷举了 64 组 head/恢复槽位，分支测试覆盖执行同时提交 0/1/2 条更老指令及回绕。旋转选择器还对 8/32/64 项阵列各做了 20,000 次随机推进验证。

v19 的最差路径起点已追到缓存 waiter 寄存器的写入块，终点是 IQ 操作数寄存器的写入块；路径串联等待请求优先选择、缓存返回/新请求读地址选择、待写数据旁路和唤醒。v21 将优先选择移到已有缓存状态更新的时钟边界之前，同时使用 waiter 与 word-valid 的下一状态保存返回标签、错误及地址，保持返回周期。六项性能周期与 v19 完全一致，但默认频率暂为 141.16 MHz，因此没有替换已验证版本。新增返回端测试按已发布的 waiter/word-valid 状态逐周期计算独立的选择与返回数据预期，完成 12,012 次检查，覆盖 568 个 miss、43 个错误、198 次返回停顿和 549 个多请求并行周期；v19 与 v21 得到相同计数。

v21 的中间网表进一步确认最差路径为 `frontend.pc[7] → frontend.fifo[7][64]`。v22 将 PC+4 和 PC+8 独立用保留层次的前缀 AND 网络计算，没有增加寄存器或周期。递增测试覆盖 8/29/30/32 位的所有进位长度、溢出和每组 20,000 次随机输入。该版的最差路径转到内存 IQ 选择、有效地址加法和 512 字缓存地址译码；一个读地址控制节点扇出 260，随后节点扇出 43，二者累计约 2.99 ns。

v23 在现有操作数寄存器前局部化唤醒与反馈，40,000 次随机状态序列验证准备、持有、多个写回匹配及优先级；它单独综合只有 126.40 MHz。v24 再将缓存数据读取拆成 8 个 64 字局部读取和一个 8 项选择，每个 bank 保留真实综合边界，面积和全部门延迟仍由原流程计入。组合后达到 153.77684337 MHz，周期 6.5029296875 ns；六项性能与 v19 逐项相同，完整 RTL 与 19 项正确性均通过。不能由此推断单独局部唤醒有效，后续还需拆开对照。

## 第二个参考仓库复测

用户新提供的 [ACM-CPU](https://github.com/Galuisss/ACM-CPU) 固定到 `perf-redesign` 分支的提交 [3df298e9](https://github.com/Galuisss/ACM-CPU/commit/3df298e94598e0ba0d6f478a7147039e411bbf19)。通过已连接的 GitHub 读取导出 RTL，校验 git blob 哈希，使用本仓库的默认综合、构建和性能脚本复测。导出 `cpu.v` SHA256 为 `287396f1b535ebf1a6f0d82c862d1c402dfbd45f575c14f6bb25fcd8bed9256f`；快照元数据与实测报告保存在 [参考测量目录](data/2026-10-02/timing-stage4/reference-galuisss-standard/)。

实测 **206.65993945 MHz、4.8388671875 ns、14,344.46 μm²、IPC 1.04479765**。双发射架构、同步 FakeRAM 缓存和局部控制结构可以借鉴，但该配置仍低于 IPC 1.0985 的要求，不能直接替换。六项性能答案校验及本仓库 19 项完整正确性测试均通过。

可验证的候选是：在已有时钟边界保存 ROB head 前缀、下一拍空间许可和局部读取选择，减少全局 head/control 扇出；以及在现有缓存和 IQ 寄存器之间提前计算地址。每项只在正确性、IPC、面积和默认频率都验证后保留。153.78 MHz 仍距离目标很远；参考复测必须把频率与架构宽度、缓存和 IPC 一起比较。
